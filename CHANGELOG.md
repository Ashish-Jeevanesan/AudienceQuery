# Changelog

All notable changes to this project will be documented in this file.

## [2026-10-17] - Theme Song Voting (4 modules)

- **New voting feature, designed and approved via a shared Artifact review before any code was written** (see the design doc's Open Questions thread for the decisions behind every choice below). Four modules:
    1. **Manage Votings** (admin-only, new drawer in the Moderator screen): write a question (with optional Hindi/Odia translation fields + the same AI Translate button event titles already use), add 2+ options (each with an optional photo via the same signed-upload pattern as event branding), then move it draft → open → closed. More than one voting can be open at once -- no auto-close.
    2. **`/vote`** (new, public, no login, EN/HI/OR): shows whichever voting(s) are open -- straight to the options with exactly one, a short picker first with more than one. Picking an option asks for name, phone, and date of birth.
    3. **Vote Monitor** (new drawer, admin OR moderator -- not admin-only, unlike Manage Votings): every vote cast, with auto-computed suspicion badges, and a one-click Invalidate/Reinstate that excludes a vote from every tally immediately.
    4. **`/vote/stage`** (new, standalone page with its own sign-in, admin/moderator/stage): a projected live results screen -- animated bars per option, updating in real time over the app's existing SSE stream (`voting:tally` events), no polling. Staff pick which voting to project, including an already-closed one, so a final result can stay up after a poll ends.
- **Anti-duplicate-vote design**: phone number is the *only* hard block -- a real `UNIQUE(voting_id, voter_phone)` constraint enforced by Postgres itself. Name is stored as typed and is never part of the dedup key, so the obvious trick (resubmitting as `GRACE` instead of `Grace`) cannot open a second vote; verified live by submitting the same phone with a different name case and getting a 409. Date of birth, IP address, and a client-computed device fingerprint (hashed entirely in-browser via `crypto.subtle.digest`, no new dependency, no raw signal ever sent) are captured per vote but deliberately never used to block one -- a venue's shared WiFi puts many real attendees behind one IP, and a shared device isn't automatically fraud. Instead they feed `suspicion_flags` (`shared_device`, `ip_burst`, `implausible_dob`), informational badges a human reviews in Monitor; confirmed live that a second vote from an already-seen device gets auto-flagged without being blocked.
- **New tables** `votings`, `voting_options`, `votes` (migration 25 in `database/schema.sql`), plus a `voting-media` Storage bucket for option photos -- same default-deny RLS and soft-delete conventions as every other table in this project.
- **Note**: `/root`'s chooser now shows three options (Ask a Question / Raise a Complaint / Vote) instead of two.

## [2026-10-13] - Admin Rules Tab, Role Access Hints, Multi-Event Moderator Fixes

- **New admin-only "Rules" tab in the Moderator screen**: both `rules` table switches (`complaints_open` and the `prod_release` chooser rollout flag) can now be flipped from the UI instead of needing direct Supabase access. New `PATCH /api/rules/prod-release` (admin-only, mirroring the existing complaints-open endpoint) backs it.
- **Manage Users now shows what each role actually unlocks**, next to its checkbox (e.g. "Moderator: Moderator screen + Manage Artifacts", "Panelist: Panel screen") instead of just the bare role name -- makes it obvious what access you're granting before you save.
- **Moderator screen's status KPIs (Review Inbox/Panel Queue/Live on Stage/Public Feed/Answered) now respect the selected event.** Previously these always totaled across every event regardless of the "All Events" dropdown, so picking a specific event narrowed the question list below but left the counters above showing the old totals -- confusing when working one event at a time. The matching tab badges share the same fix.
- **With exactly one event currently open, the Audience/Panel/Stage "pick an event" screen is skipped entirely** -- there's nothing to choose between, so a bare `/ask` visit now routes straight to that one event instead of making the visitor select it from a dropdown first. Only applies when no event is already selected (a direct `/e/:joinCode` link, or an event already chosen, is left alone); with zero or multiple events open, the picker still shows as before.
- **Fixed a confusing "Pause questions" button on already-expired events** in Manage Events: expiry (`isExpired`, a date-based hard cutoff) and the manual accepting-questions toggle are independent, so an expired event could still show a clickable "Pause questions" control that had no real effect (the event's already closed via expiry either way). That control is now disabled and relabeled "Expired" for any event past its expiry date.

## [2026-10-11] - Complaints Intake Kill Switch, Guide Link Everywhere

- **New admin/management control to stop accepting new complaints on demand** (e.g. an overflow of tickets at a live event): a second entry in the `rules` table, `complaints_open` (default `'Y'`), checked server-side in `POST /api/complaints` -- closing it returns a 403 rather than silently relying on the client to hide the form. A new "Intake open"/"Intake paused" toggle button in the Complaints Dashboard header (`PATCH /api/rules/complaints-open`, admin/management-only) flips it instantly, no deploy needed; `/complain` polls the paired public `GET /api/rules/complaints-open` on load and shows a "Not accepting complaints right now" message in place of the form while it's off (the status-lookup tab stays available either way, so people can still check tickets already filed). A read failure on either endpoint fails *open* (treats it as accepting), so a transient DB hiccup can't silently block every submission.
- **Note**: questions already had an equivalent, pre-existing per-event control -- the "Pause questions" button in the Moderator dashboard (`is_accepting_questions` on the `events` table) immediately stops new question submissions for that event and shows a closed message in the Audience view. No change was needed there; this entry just closes the matching gap that existed for complaints.
- **Guide link added to every screen**: the shared `Footer` (visible to all users, not just admins) and the header of every standalone page that doesn't use it (`/root`, `/complain`, `/dashboard`, `/logs`) now link to `/guide`.

## [2026-10-09] - Complaints Dashboard (Phase 2), True Multi-Role Support, Chooser Screen + Rollout Flag

- **New `/dashboard` complaints management screen**, gated to the `admin` and new `management` roles: a mobile-friendly, fuzzy-searchable list (via `fuse.js`, matching on ticket number/name/phone) with status tabs, driving each complaint through a fixed 3-step workflow enforced both in the UI and server-side (`PATCH /api/complaints/:id/acknowledge|assign|resolve`) -- **categorize** (pick from a fixed set of categories) → **assign** (free-text name, e.g. "Raju - Electrician", not tied to a system account) → **resolve** (optional photo, uploaded via a signed Storage URL to a new `complaint-media` bucket, same pattern as event branding uploads). Each complaint's detail view shows a timeline with per-stage durations and a total "time taken" marker once resolved.
- **Public status lookup added to `/complain`**: a "Check Status" tab lets the original submitter check progress with just their ticket number + phone (both must match, so a leaked/guessed ticket number alone can't expose someone else's complaint) -- shows the same timeline, category, assignee, and resolution photo.
- **New `management` role, and true multi-role support**: `users.role` (one role per account) is replaced by a `user_role_assignments` many-to-many table -- an account can now hold any combination of `admin`/`moderator`/`panelist`/`stage`/`management` (e.g. moderator + management without being a full admin). Every `requireRole()` check now grants access on any overlap rather than equality against a single value; "Manage Users" shows checkboxes instead of a dropdown; the header's view-switcher now supports e.g. a panelist+stage-only account switching between just those two views instead of being locked to one. The last-remaining-admin lockout guard was preserved across the migration.
- **New chooser screen at `/root`**: "Ask a Question" (→ `/ask`, the existing flow) or "Raise a Complaint" (→ `/complain`), localized EN/HI/OR. A direct link to a specific event (`/e/:joinCode`) is unaffected either way.
- **Rollout gated behind a new `rules` table** (`prod_release` flag, default `'N'`): until flipped to `'Y'` directly in Supabase, bare `/` and any unrecognized path keep going straight to `/ask` -- exactly what every already-printed/shared QR code and link expects -- rather than surfacing the new chooser before it's ready. `/root` stays directly reachable either way. No code change or redeploy needed to flip it live.

## [2026-10-08] - Complaints Portal, Phase 1: Public Submission Form

- **New standalone, unauthenticated route `/complain`**: a single global complaint box (not tied to any event, unlike questions) collecting name, phone number, and complaint text. Built for very basic users on mobile (95% of expected traffic) — one card, three fields, no login, no event picker, full English/Hindi/Odia support and the same light/dark theming as the rest of the app, reusing the existing `.input-base`/`.btn-primary`/`.card` design tokens so it required zero new CSS.
- **`POST /api/complaints`** (public, no auth): validates name/phone/complaint length and a plausible phone number (7–15 digits, optional leading `+`), normalizes the phone to digits-only for future dial/message use, and inserts into a new `complaints` table. Returns a short `ticket_number` (e.g. `CMP-9F3A2B1C`) — the only handle the anonymous submitter has to reference their complaint later, shown on-screen with a copy button.
- **New `complaints` table** (`database/schema.sql` migration 20), deliberately separate from `questions`: RLS enabled with no permissive policies (default-deny, same posture as `events`/`users` — all writes go through the server's service-role client, which validates input first). Already includes `status`/`assigned_to`/`internal_notes`/`resolved_at` columns, unused today, so the planned phase-2 management dashboard (its own separate login, not the existing admin/moderator/panelist/stage roles) won't need a migration against a table full of live complaints.
- **Scope note**: this is phase 1 only — a write path with no read/management UI yet. Viewing, assigning, annotating, and resolving complaints is an explicitly deferred phase 2, to be designed separately. A WhatsApp status-update notification on top of this was asked about: feasible in principle (the normalized `phone` column is ready for it), but needs a WhatsApp Business/Cloud API (or a provider like Twilio) account and message-template approval on the business side before any code can send one — not something that can be wired up from this codebase alone.

## [2026-09-03] - Event Branding (Logo + Hero Banners), Soft-Delete Events, Security Hardening

- **Per-event logo and hero banner carousel**: moderators can now upload a logo (replaces the default "AQ" mark in Header, Footer, and Stage when set) and up to 3 banner images per event (crossfading ambient carousel behind the Audience hero text, via a new `HeroBannerCarousel` component) from a new "Manage Artifacts" drawer. Uploads go through signed Supabase Storage URLs — the browser uploads directly to Storage, never proxying image bytes through the Vercel serverless function — with client-side canvas compression (long edge capped at 1920px, ~400KB target) before upload. Zero visual change for events that never upload branding.
- **Event soft-delete**: a new `DELETE /api/events/:id` (admin-only) flips an irreversible `is_deleted` flag on the event and every question belonging to it together, and immediately purges the event's Storage images. There is no restore path. Every list-serving query (`GET /api/events`, `GET /api/events/open`, `GET /api/state`, join-code resolution) now excludes soft-deleted rows. An admin-only archive view for browsing deleted events/questions is deferred to a future pass.
- **Security hardening pass**, prompted by investigating a permissive RLS policy on `categories` (anyone holding the public anon key could insert/update/delete categories directly via Supabase's REST API, bypassing every admin check in `server.ts`) that surfaced several other pre-existing gaps once the database's security advisor was run:
    - Dropped the unsafe `categories` policies and dead `questions` policies gated on Postgres session variables the app never sets.
    - Found two unused `SECURITY DEFINER` views (`questions_with_categories`, `dashboard_stats`) readable by the anon key, bypassing RLS entirely — `questions_with_categories` exposed every question's raw `session_id`/`device_info`/`network_info` (including IP addresses) regardless of status, a real PII leak with no app code involved. Confirmed via `grep` that `server.ts` never references either view before revoking access.
    - `user_roles` (a 4-row static enum table, not per-user data) had RLS fully disabled with the anon key holding full read/write — locked down to the same default-deny posture as every other table.
    - The auth-signup trigger function was directly callable via RPC by anyone (a Postgres default for `SECURITY DEFINER` functions); revoked the `PUBLIC` execute grant it actually needed revoking from — revoking from `anon`/`authenticated` directly turned out to be a no-op, since they inherit through `PUBLIC`.
    - Verified safe throughout via `grep` confirming the frontend never queries Supabase tables directly (the anon-key client is used only for Auth) — every fix removed attack surface with zero functional risk, confirmed by a live smoke test afterward.
- **Built as small, single-file tasks after two earlier multi-file attempts caused real collateral damage** (a schema.sql rewrite that lost the entire migration history, and a `ModeratorView.tsx`/`App.tsx` edit that deleted 1500+ lines of real functionality and replaced it with dummy stub components) — both were caught in review and fully discarded before merging, never shipped. The final implementation was rebuilt as ~10 single-file tasks, each verified independently (`tsc`, diff review, and live end-to-end browser testing) before being accepted.

## [2026-09-02] - Question Auto-Classification: Fixed End-to-End, Measured Accuracy Eval Added

- **Fixed three separate, compounding bugs that made Gemini auto-classification silently non-functional in production**, found by testing directly against the live site rather than trusting code review alone:
    1. `GEMINI_API_KEY` had never been added to Vercel's production environment variables — only existed in the local `.env` — so every classification call failed with "Gemini API key not found" and silently fell back to no category.
    2. Once the key was added, classification still failed: the hardcoded model name `gemini-1.5-flash-latest` had been retired from the Gemini API (`404 NOT_FOUND`). Switched to `gemini-flash-latest`.
    3. Even with a valid model, classification was unreliable: the prompt constrained the model to a valid category ID via `responseSchema`'s enum, but never told the model what any of those IDs actually meant, giving it no real signal to pick correctly among them. The prompt now includes the id→name mapping for every category.
- **New reusable accuracy eval** (`scripts/eval-classification.ts`, run via `npm run eval:classify`): extracts `classifyQuestion()` into its own module (`src/classify.ts`) so the eval calls the exact production code path rather than a copy that could drift, fetches the live category list from Supabase at runtime, and runs a 26-question labeled test set (24 single-answer + 2 deliberately ambiguous, scored separately) against the real Gemini API — zero writes to the `questions` table.
- **Found and fixed a real timeout/accuracy tradeoff via the eval, not guesswork**: at the original 3-second timeout, roughly 19% of real classification calls aborted before completing, each one silently failing open with no category — the dominant failure mode, not prompt quality. Separately, generic/logistical questions (e.g. "What time does the conference end today?") consistently returned no category even though a general/open-discussion category existed for exactly that case, because the prompt never named it as the preferred fallback. Fixed both: timeout raised to 7 seconds, and the prompt now generically prefers "whichever category best represents general/open discussion" over returning nothing for non-specific questions — worded without hardcoding a category name, since categories are defined per event/moderator and the name may differ.
- **Verified via three independent eval runs** (26 questions each): 100% strict accuracy (24/24), 100% ambiguous accuracy (2/2), zero timeouts.

## [2026-08-31] - Multi-Event Mode: Join-Code Routing Replaces the Single "Live Event" Singleton


- **Retired the single-`is_live`-event model.** Until now exactly one event could be live at a time (a partial unique index plus an atomic `activate_event()` function), and every visitor landed on whichever event held that flag — making it impossible to run two concurrent groups side by side. Any number of events can now be `is_accepting_questions = true` at once, each independently reachable via its own `/e/:joinCode` link. Migration drops `is_live`, `one_live_event`, and `activate_event()`; `getLiveEvent()` is replaced server-side by `getEventByJoinCode()`.
- **New public `GET /api/events/open` endpoint** powers a "pick an event" dropdown — every event currently accepting questions, in a narrow public-safe shape (no join codes beyond the one being offered, no admin-only fields). Excludes expired events even if still manually marked accepting.
- **Event dropdown now lives in the Header on Audience, Panel, and Stage — always, not just when nothing's picked yet.** Previously an event, once selected, was locked in for the session; now switching events is one click away from any of those three screens. Moderator is the one exception: it never shows the dropdown, since it already gets every event unfiltered in its own dashboard (its "event filter" lists all of them, expired included).
- **Event expiry**: new optional `events.expires_at`. Once past, an event drops out of the public dropdown and rejects new submissions (`"This event has ended..."`), independent of its manual accepting-questions toggle — but stays fully visible, with all its questions, in Moderator.
- **`POST /api/questions` now takes `eventJoinCode` from the client** instead of implicitly targeting whatever was live; each event's own `is_accepting_questions`/expiry is the only gate, enforced server-side (not just hidden in the UI).
- **Verified directly against the live Supabase project** (`aq-live-v1`): `GET /api/events/open` returns real event data post-migration, `GET /api/state?event=<code>` correctly resolves a join code to its event (including `isExpired`) with its real questions/categories, and `npx tsc --noEmit` passes clean. Also surfaced and fixed a live production bug in the process: the previously-committed `server.ts` was still querying the already-dropped `is_live` column, so `/api/state` was broken against the current database until this change landed.

## [2026-08-27] - Going Mobile, Screen 5: Logs Page — Pass Complete

- **Fixed a log line rendering 4,337px tall on a 390px phone.** Ordinary INFO-level logs (e.g. `Questions fetched from database`) embed their payload as whitespace-free JSON; the log viewer wrapped messages with `break-all`, which — once the level badge and timestamp ate most of a mobile row's width — forced a several-hundred-character blob into hundreds of stacked single-word lines. With auto-refresh and auto-scroll both on by default, this meant a moderator checking logs from their phone could land mid-wall-of-text on every 5-second refresh instead of at the actual latest entry. Fixed by switching each log message to a horizontally-scrolling single line (the same convention a terminal or browser DevTools console uses) instead of vertical wrapping: ordinary short messages look identical, and only the rare giant-JSON line gets its own scrollbar instead of destroying the page.
- **Bumped the Logs page's header controls to the 40px tap-target standard** — the back button, all 3 action icons (auto-scroll, pause/resume, refresh), the search box, and the level filter were all 30–32px.
- **This closes out the "Going Mobile" responsiveness pass.** All 5 screens (Audience/Header, Panel, Moderator, Stage, Logs) have been audited and fixed at real mobile viewport widths.

## [2026-08-21] - Translate Assist for Category & Event Names

- **"Translate" button on moderator-entered names**: the Manage Categories form and both event forms (create + inline edit) in `ModeratorView` now have a Translate button next to their Hindi/Odia fields — it fetches a draft translation from the English text, which the moderator can then correct before saving.
