## Real-time broadcast is unreliable in production (mitigated, not fixed)

- **The underlying issue**: `server.ts`'s SSE broadcast (`/api/stream`, `broadcastStateUpdate()`) holds connected browsers' `res` objects in a module-level `clients` array and loops over it on every write. That only works within one persistent Node process. In production this app runs on Vercel as serverless functions (`api/index.ts`) -- every request can be served by a different, independently-scaled function instance with its own memory, so a write handled by instance B has no way to reach an SSE connection held open by instance A. The connection doesn't error, it just never gets told about the update. This is invisible in local dev (`npm run dev` is one process), which is why it took a production report ("leave the Stage screen open, a panelist's update doesn't show until refreshed") to surface it, even after a lot of local SSE testing this session (including the new voting feature's live tally).
- **Current mitigation (2026-10-20)**: every screen built on `useRealTimeQnA` now also re-fetches full state every 15s regardless of SSE, and `/vote/stage` re-fetches every 8s -- bounds the staleness to one poll interval instead of "until someone refreshes," without touching the broadcast architecture itself. Good enough for a projector-style display; not a fix for the Moderator/Panel screens getting instant cross-instance updates in every case, though those are usually being actively operated by someone who can tolerate a few seconds' lag.
- **The real fix**, if sub-second realtime across instances matters later: move broadcast off the in-process `clients` array onto something that isn't tied to a single serverless instance -- Supabase Realtime (this app already depends on Supabase) is the natural fit, since it's a separate always-on service any instance can publish to and any client can subscribe to directly. That's a real rearchitecture of every `broadcastStateUpdate()` call site, not a small patch -- deliberately not started without an explicit go-ahead.

## Question export (Excel/Word/PDF) -- remaining follow-up

- **PDF export: an Odia-dominant question line that also contains actual English words** (e.g. "Sir ... Question ...") shows boxes for just those words. Root cause: Noto Sans Oriya's complete font release has digits/punctuation but not full Latin letters, and this feature picks one font per line (by dominant script) rather than switching fonts mid-line, since the latter was tried first and visibly broke the text baseline. Confirmed against a real 47-question export: this affected exactly 1 question; every pure-English/Hindi/Odia question (digits and punctuation included) rendered correctly either way. A full fix means either finding a complete Oriya-script font that also has full Latin coverage, or solving the mid-line font-switch baseline problem (manually computing each font's ascent at the given size and vertically offsetting each segment to a shared baseline, rather than relying on PDFKit's own per-call positioning) -- not started, since the residual impact is narrow.

## In progress — resume when Gemini Implementer is back

- **Auto-select a question's category via Gemini, instead of the audience picking one manually.** Frontend half is done: the "Topic (optional)" picker and its state are removed from `AudienceView.tsx`, and `categoryId` is gone from `submitQuestion`'s signature in `useRealTimeQnA.ts` — the client no longer sends one at all. Server half is broken and needs a real fix, not a re-report:
  - `server.ts` gained a `classifyQuestion()` helper wired into `POST /api/questions`, but **it always returns `null`** — verified directly by submitting a clearly parenting/faith-themed question against the real category list and getting `categoryId: null` back, with nothing logged at the failure point. Root cause: the Gemini call uses `responseMimeType: "application/json"` with a free-text prompt but no `responseSchema`, so the model's JSON key names aren't constrained to match what the code reads (`parsed.categoryId`) — it silently returns wrong-shaped JSON, and `categoryIds.includes(chosenId)` fails with zero diagnostic trail. Fix is to use `@google/genai`'s `responseSchema` (enum-constrained to the real category ids) instead of prompt wording alone.
  - It also added a **new, unwanted dependency**, `@google/generative-ai` (an older/separate SDK), instead of the already-installed `@google/genai` it was told to use — needs removing from `package.json`/`package-lock.json` once the classifier is rewritten against the right package.
  - No timeout around the Gemini call yet (a ~3s cap was asked for, to keep a slow API call from ever stalling question submission) — still missing.
  - Leftover dead code: `categoryId` is still destructured from `req.body` in `POST /api/questions` in `server.ts` even though nothing uses it anymore.
  - **A specific correction task is already sitting open on the Cog pinboard** (unclaimed — "CORRECTION: auto-category classifier doesn't actually classify — fix root cause, don't just re-report") with all of the above spelled out, ready to be picked up as soon as Gemini Implementer is restarted (it got stuck in a retry loop on its own backend's 400 errors, unrelated to this code, and needs a manual restart).
  - A real `GEMINI_API_KEY` is already set in the local `.env` — that part's not blocking.
